# trace

The backend's session traces: append-only files of encrypted records, and the
key hierarchy that decides who can read them and when.

Read [`readme.md`](../readme.md) for what john is and
[`protocol/readme.md`](../protocol/readme.md) for the wire. This is the key hierarchy, the
file format, and what the encryption does and does not protect against.

The backend keeps a complete record of every session. It has to: that record is
the product's reason for existing, and it is written by the backend rather than
the client precisely so that a developer cannot edit their own history. But
"the backend writes everything down" and "the backend can read everything, for
ever, from a stolen disk" are two different properties, and only the first one
is wanted.

The claim this makes, stated as narrowly as it is true:

> The backend can read a session while a client is connected to it, and cannot
> read it before or after. A stolen database, a stolen backup, or a server
> compromised tomorrow yields nothing about yesterday.

It is not end-to-end encryption and this document never pretends otherwise. The
backend builds every model request, applies replacements, and routes — it
cannot do any of that without the plaintext in front of it. What it gives up is
the ability to read that plaintext *at rest*.

## The three keys

**The organization key** — an X25519 key pair generated by
`john backend --setup`, which prints the private half to the operator's
terminal once and keeps only the public half, in `org.trace_key`. It is printed
rather than shown in the browser so that it never reaches the database, an HTTP
response, or a log; the terminal that prints it already prints the one-time
setup URL, and whoever can read that output is trusted to bootstrap. An
operator who would rather hold a key they generated themselves pastes its
public half into the setup form, and the generated one is discarded.

Setup will not complete without one, and the recipient is validated there — a
typo would otherwise be silent, leaving a backend with no trace writer and
every appearance of working.

**The user key** — an X25519 key pair the client generates the first time a
developer signs in, kept at `~/.john/trace-identity.txt` (mode 0600). The
public half is registered with the backend on `session.open` and stored on the
user row. The backend never sees the private half. Signing in again does not
re-key: a new key would silently cost the developer every session they can
currently read.

**The session key** — 32 random bytes the backend mints when a session starts,
different for every session. This is the key that actually encrypts anything.
The other two exist only to carry copies of it.

Both key pairs are ordinary age keys, so an operator can generate, store and
rotate them with `age-keygen` and whatever they already use for secrets.

## The trace file

One file per session, under the year the session *started* — not the year of
each record, so a conversation that runs past New Year keeps writing to the
file that holds its header and its key.

```
trace-store/2026/s_7Yk4mQ.jsonl

  line 1   {"seq":1,"v":1,"session":"s_7Yk4mQ","started":"…","alg":"chacha20poly1305",
            "keys":[{"for":"org","wrapped":"<base64 age ciphertext>"},
                    {"for":"u_3f1a","wrapped":"<base64 age ciphertext>"}]}
  line 2   {"seq":2,"c":"<base64 nonce ‖ ciphertext>"}
  line 3   {"seq":3,"c":"…"}
  …
  line 41  {"seq":41,"grant":"u_3f1a","wrapped":"<base64 age ciphertext>"}
```

`keys[].wrapped` is the session key encrypted to that recipient's public key
with age. Two copies are written when the session opens: one for the
organization, one for whoever the session belongs to.

Putting them in the file rather than in SQLite is what makes the trace store
restorable on its own. The readme tells operators to back up the database and
the trace store, and a trace store that cannot be decrypted without a matching
database is a trap waiting for the day the two backups disagree. A file plus a
private key is enough; nothing else is needed. **No key material is in the
database at all.**

`grant` lines are how a recipient is added later — see
[Losing a key](#losing-a-key). They are appended, never edited, so the file
stays append-only in the strict sense: no byte written is ever changed. A
reader collects key material from the whole file before decrypting anything,
because a grant is issued after the records it opens.

### Records

Each record is the JSON `Record` in [`trace.go`](trace.go), encrypted with
ChaCha20-Poly1305 under the session key, with a **random 12-byte nonce stored
on the line**.

Each record uses a random nonce so nonce generation is independent of sequence
number bookkeeping. Reusing a nonce with the same key compromises encryption.

### Sequence numbers

`seq` is a line's position in its own file, starting at 1 for the header. A
reader checking that the numbers run 1..n with no gaps can tell that no line
has been removed; the console shows a warning when they do not.

Sequence numbers must continue across reconnects and backend restarts. Two
constraints prevent duplicate numbering:

- The writer recovers the count from the file the first time it touches one, so
  a backend restart continues the file instead of restarting it.
- The backend keeps **one** writer (`Server.traceWriter`), so concurrent
  sessions share a counter per file rather than racing with separate mutexes.

`TestSequenceNumbersContinueAcrossWriters` in [`trace_test.go`](trace_test.go)
checks that reopening a file continues its numbering.

## A session, from open to resume

**Open.** The backend mints the session key and holds it in memory. It writes
the header with two wrapped copies: the organization's, and the public key of
the user the session belongs to. From that moment it retains no way to recover
the key once it leaves memory.

**Working.** The key is in memory, so the backend encrypts with it: trace
records on the way to disk, and the agent state it writes to `sessions.state`
at every message boundary. That column holds an opaque `enc:v1:…` envelope
instead of `agentkit.State` JSON in the clear. Nothing else about the agent
loop changes.

**Parked.** A client disconnects; the session stays in the hub's memory and so
does the key. Nothing on disk has changed.

**Restart.** The backend loses the key with the rest of its memory. What
remains is an encrypted trace file, an encrypted `sessions.state`, and two
wrapped copies of a key it cannot open. The session is now unreadable to it.

**Resume.** On the next `session.open` the backend reads the header, finds the
copy wrapped for that user, and sends it down as `session.key.request` — still
encrypted; it is handing the developer their own copy. The client opens it with
the private half on the machine and returns the key. The backend decrypts its
own `sessions.state` and carries on. See
[Unlocking](../protocol/readme.md#unlocking).

**When the client cannot open it.** A re-keyed machine, or a lost identity.
The backend starts a *fresh* session rather than continuing one that silently
lost its history, and the client says so.

## Why the client sends a key and never a conversation

There is an obvious-looking shortcut here that is wrong, and it is worth
writing down so nobody rediscovers it as a good idea.

The client already receives nearly the whole conversation — `message.delta`,
`tool.call`, `tool.result`, `prompt` — so it could keep its own encrypted copy
and hand it back on resume, and the backend would never need to decrypt
anything. It is a tempting design and it destroys the load-bearing property of
the system.

If the backend rehydrates a session from something the client wrote, the client
decides what the conversation was. It can add an assistant turn that never
happened, drop the `model.narrow` that did, or return content with the
replacements undone. Every control in `controlStreamer` operates on history the
backend believes to be true. The loop was put in the backend so that history is
not the laptop's to author, and accepting a client-supplied transcript walks
around that on the way back in.

So the rule, and it is the whole design in one line: **the client holds keys,
never content.**

(If a client-carried blob is ever genuinely wanted — to make the backend
stateless — the backend must authenticate what it wrote, so it can reject
anything it did not produce verbatim. There is no statelessness to win here:
the state is already in SQLite, written every message.)

## Reading a trace

**A developer** reads their own sessions with the key on their machine.
`/resume` in the client is the first thing built on it: it lists this
workspace's conversations and carries one on.

**An administrator** reads any session in the console's Traces page: paste the
organization private key, and the browser fetches sealed files from
`GET /api/v1/traces/{session}/file` and decrypts them locally
([`console/src/lib/trace.ts`](../console/src/lib/trace.ts)). The key never
reaches the backend — there is no endpoint that would take it — and it is held
in a module variable for the life of the tab, deliberately not in
`localStorage`, where a read key would outlive the sitting.

**The backend** reads nothing it is not currently connected to.

Both readers open the same bytes, and a shared fixture
(`console/src/lib/__fixtures__/trace-fixture.json`) is decrypted by both test
suites so the two implementations cannot drift apart quietly. There is one
file format and one protocol version; older formats are not supported.

## Losing a key

A developer who loses their machine loses the ability to read their older
sessions. Nothing is destroyed: an administrator holding the organization key
opens the session key in the browser, re-wraps it for the developer's new
public key, and `POST /api/v1/traces/{session}/grant` appends it to the file.
That is a small operation on 32 bytes per session and it never touches the
records. The backend is handed a key already wrapped for the recipient, never a
plaintext one, which is why the endpoint cannot be used to read anything.

It is deliberately an action a person has to take. There is no escrow, no
recovery passphrase, and no path by which the backend restores access on its
own — because any such path is also the path an attacker takes.

## What this does not protect against

- **A backend compromised while you are working.** The key is in memory and the
  plaintext is passing through. Unavoidable for as long as the backend is the
  one calling the model.
- **The model provider.** Content leaves for a provider by design; that is what
  the replacement and routing policies are for, not this.
- **Traffic analysis of the store.** File names, sizes, timestamps and record
  counts are not hidden. Who worked, when, and roughly how much is visible to
  anyone holding the disk.
- **A malicious operator.** Whoever holds the organization private key reads
  everything. That is the intended power of the role; the control on it is the
  change history, which records what administrators did — including every
  trace grant.

## Known limits

**One key per user, so a second machine re-keys.** The user row holds one
recipient, and a client registers whichever key its machine holds. Signing in
on a second machine generates a second key and takes over registration, so
sessions opened before that are readable only on the first machine. Copying
`~/.john/trace-identity.txt` across machines works; so does an administrator
grant. Per-device keys would be the real fix.

**Sessions opened before a developer registered a key** get a header with only
the organization's copy. The session works and the developer cannot read it
back until an administrator grants them; the console shows which developers are
in that state.

**A trace store can still be absent, but not through setup.** Nothing that
completes `--setup` produces an organization without a key, and the code path
for one that has none — state stored in the clear, no records written — remains
only so that a hand-written or half-migrated row degrades visibly rather than
crashing. The console's organization panel shows the absence.

**Out-of-session records have nowhere to go yet.** Nothing writes a trace
record outside a session today. When `POST /api/v1/proxy/decisions` lands, those
records will arrive with no session and so no session key, and will need their
own grouping with its own key, wrapped for the organization and for the
developer whose machine reported them.

## Standalone

Standalone holds both roles on one machine, and the two identities are
different files: the organization's is
`~/.john/standalone/trace-identity.txt`, minted on first run, and the
developer's is `~/.john/trace-identity.txt`, the same one a signed-in client
uses. A solo developer is their own administrator and holds both.
